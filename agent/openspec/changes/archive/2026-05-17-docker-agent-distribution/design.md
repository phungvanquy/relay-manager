## Context

The relay-manager dashboard is distributed as a Docker image (`phungvanquy/relay-manager:latest`). The image currently bundles only `relay-agent-linux-amd64` and `relay-agent-linux-arm64` in `/app/releases/`. The releases API route has a hardcoded allowlist of these two files. The bootstrap script generated by the bootstrap API only detects x86_64 and aarch64.

With the multi-arch build system now producing 11 platform binaries, the Docker image and API need to serve all of them.

## Goals / Non-Goals

**Goals:**
- Docker image includes all 11 platform binaries in `/app/releases/`
- Releases API serves any valid platform binary without a hardcoded allowlist
- Bootstrap script detects all supported architectures (ARM, MIPS, FreeBSD, Darwin)
- Single command at project root builds agent binaries + Docker image
- Deploy compose continues to work with bind-mounted `releases/` directory

**Non-Goals:**
- Multi-platform Docker image (the dashboard itself only needs to run on linux/amd64 or arm64 — the agent binaries inside are cross-compiled)
- Automatic Docker Hub publishing (CI/CD concern)
- Serving compressed archives via API (bootstrap downloads raw binaries)
- Agent auto-update mechanism

## Decisions

### Dynamic allowlist based on filesystem instead of hardcoded array

Instead of maintaining a static `ALLOWED_FILES` array, the releases API will scan the `releases/` directory and serve any file matching the pattern `relay-agent-{os}-{arch}`.

**Rationale:** Adding a new platform target shouldn't require a code change. The filesystem is the source of truth for what's available.

**Alternative considered:** Keep the hardcoded list and update it. Rejected because it creates coupling between the build system and the API code — easy to forget when adding targets.

**Security:** Validate filename against a regex pattern (`/^relay-agent-[a-z]+-[a-z0-9]+$/`) to prevent path traversal or serving unintended files.

### Root Makefile orchestrates the full build

A `Makefile` at the project root coordinates:
1. `make agent` — builds all agent binaries into `releases/`
2. `make docker` — builds the Docker image (which copies from `releases/`)
3. `make all` — does both in sequence

**Rationale:** Keeps the build reproducible in one command. The agent Makefile handles cross-compilation; the root Makefile handles the integration.

### Keep `releases/` as the interface between agent build and Docker image

The existing pattern of `releases/` as a directory of binaries works well:
- In development: `docker-compose.yml` bind-mounts `./releases:/app/releases:ro`
- In production: binaries are baked into the image via `COPY releases/ /app/releases/`

**Rationale:** No change to the existing deployment model. Just more files in the same directory.

## Risks / Trade-offs

- **Image size increase**: ~45MB additional binaries (from 2 → 11 targets). → Acceptable for a server-side image. Could add a `PLATFORMS` build arg to limit targets if needed later.
- **Build time**: Cross-compiling 11 targets takes ~3-5 minutes. → Only needed for releases, not development. `make build` still builds host-only for fast iteration.
- **Stale binaries in releases/**: If someone rebuilds the Docker image without rebuilding agent binaries, old versions get baked in. → Root Makefile's `make all` ensures fresh builds. Document the workflow.
